Der TCP-Scan ist wesentlich schneller als der UDP-Scan. 3.83 Sekunden im Vergleich zu 1071.11 Sekunden. Das liegt daran
das TCP eine Verbindung aufbaut und UDP verbindungslos ist. Wenn TCP einen Port scannt, dann macht er einen baut er eine
Verbindung auf mit dem Server, also bekommt eine Rückmeldung -> 3-way handshake.
Bei geschlossenen Ports wird ein Reset-Paket zurückgeschickt, bei offenen Ports wird ein SYN-ACK-Paket zurückgeschickt.
(laut ChatGPT)
Das heißt der TCP Scan ist schneller, weil er immer eine Rückmeldung bekommt. UDP-Scans hingegen bekommen keine
Rückmeldung, wenn der Port offen ist kommt nichts zurück. Wenn der Port geschlossen ist, dann kommt ein
ICMP Port Unreachable zurück. (laut ChatGPT)
Beim Scan muss also gewartet werden ob eine Rückmeldung überhaupt kommt.

Chat-GPT hat mir -T4 empfohlen, aber laut "https://nmap.org/book/man-performance.html" beeinflusst das eher Parameter
die für TCP wichtig sind, aber auch den Parameter --max-rtt-timeout, was ebenfalls für UDP-Scans wichtig ist.

- mit -F im Befehl kann man nur die beliebtesten 100-UDP-Ports scannen
- mit --max-scan-delay 100ms wartet nmap maximal 100ms bis es das nächste Paket sendet (anstatt 1sec)
- -T4 setzt unter anderem --max-rtt-timeout 1250ms, also anstatt 10 sec nur 1,25 sec warten bis eine Antwort kommt.


Ausgeführter Befehl: nmap -sU -F -T4 --max-scan-delay 100ms scanme.nmap.org

Aufgabe 4)

siehe "TokenRingDelete.java" und "Token.java" in src Ordner.

Jeder Knoten setzt einen receive-Timeout dynamisch mit der Anzahl der Knoten im Tokenring-Netzwerk -> Für
jeden Knoten +1,5 sec.
Wenn ein Knoten entfernt wird, werden die übrig gebliebenen Knoten einen Timeout feststellen und einen Ping an den
nächsten Knoten schicken, welcher mit Pong bestätigt werden muss, wenn dies nicht geschieht wird dieser Knoten gelöscht
und der Token wird an den nächsten folgenden Knoten gesendet.
Das Token.receive() wurde so angepasst, dass es einen Ping empfangen kann und auf diesen mit Pong antwortet. Im Loop wird
falls ein Ping im TokenRingDelete.receive() empfangen wird, dieses rekursiv erneut aufgerufen, damit wieder auf
das nächste Token gewartet wird. Erst wenn wirklich ein Token empfangen wird, wird der Loop weitergeführt.

Beispiel-Ablauf:

1.Knoten (Port: 62279):

Sending {"sequence":14,"ring":[{"ip":"192.168.178.21","port":62323},{"ip":"192.168.178.21","port":62279},{"ip":"192.168.178.21","port":62324}]} to 192.168.178.21:62324
Sent ping to 192.168.178.21:62324
Received pong from next Node

2.Knoten (Port: 62324):

Sending {"sequence":15,"ring":[{"ip":"192.168.178.21","port":62279},{"ip":"192.168.178.21","port":62324},{"ip":"192.168.178.21","port":62323}]} to 192.168.178.21:62323
Received ping from 192.168.178.21:62279
Return Pong to Sender
Received Ping. Return to receive.
Sent ping to 192.168.178.21:62323
No response from 192.168.178.21:62323. Node is considered dead.
Removing 192.168.178.21:62323
Removed dead node 192.168.178.21:62323 from the ring.
Sending {"sequence":15,"ring":[{"ip":"192.168.178.21","port":62324},{"ip":"192.168.178.21","port":62279}]} to 192.168.178.21:62279
Token sent to new next node 192.168.178.21:62279

3.Knoten (Port: 62323) wurde entfernt...


Hier sieht man dass der erste Knoten einen Ping an den zweiten Knoten geschickt hat, der dann mit Pong bestätigt wurde.
Bei dem ersten Knoten wird der receive-Timeout zurückgesetzt, weil der Knoten noch lebt. Dieser wird warten bis ein neuer
Token kommt. Der zweite Knoten hat den Timeout noch nicht erkannt, und wird angepingt und bestätigt mit Pong den ersten
Knoten das er noch lebt. (Received Pong. Return to receive.) Der zweite Knoten schickt dann einen Ping an den dritten
Knoten, der antwortet nicht, da er entfernt wurde.
Der zweite Knoten markiert den dritten Knoten als tot und schickt den Token an den ersten Knoten, damit der Ring weiter
arbeiten kann.
