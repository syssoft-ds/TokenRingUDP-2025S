Sliding-Window:
Wie der Name schon sagt, läuft durch das Sliding-Window etwas durch. Dabei handelt es sich um Pakete eines Senders, dessen Empfang zuerst vom Empfänger bestätigt werden muss, um einen Paketverlust zu melden. Damit dabei aber nicht zu viele Pakete gesendet werden und die Ressourcenverwendung nicht zu extrem wird, ist die größe des Sliding-Windows begrenzt. Erst wenn ein Paket erfolgreich quittiert wurde, dem Sender also mitgeteilt werden konnte, dass das Paket fehlerfrei erhalten wurde, kann ein weiteres Paket das Sliding-Window betreten. Prinzipiell kann man sich das Sliding-Window wie eine Queue mit begrenztem Speicher vorstellen, welche bei einer Menge von 0 freien Speicherplätzen die neuen Pakete so lange gesendet bekommt, bis ein Speicherort für das neue Paket frei wird, indem ein anderes quittiert wurde. 

Bei den folgenden drei TCP Protokollen ist das Ziel überall identisch: Das Netzwerk soll nie so volllaufen, dass alles verloren geht. Die drei Protokolle gehen mit unterschiedlichen Methoden an die Problemlösung heran.

TCP Tahoe:
Das Protokoll beginnt bei einer Sliding-Window-Größe von 1 und verdoppelt die Größe pro erfolgreich gesendetem Paket. Wenn das Protokoll bemerkt, dass Quittierungen ausbleiben, oder ein Paket zu lange nicht bestätigt wurde, versteht das Protokoll dies als Verlust eines Paketes an. Dann wird die Window-Sliding-Größe auf 1 gesetzt, und das Protokoll startet von vorne. 

TCP Reno:
Wenn das Protokoll wiederholt den gleichen ACK erhält, der Empfänger ein Paket verloren hat, aber weiterhin welche erhält, schickt das Protokoll das vermisste Paket sofort nochmal und halbiert die SWG. Dadurch läuft das Protokoll zwar langsamer, beginnt aber nicht immer von vorne, wie bei Tahoe der Fall.

TCP Vegas:
Das Protokoll vergleicht hier die Übertragungsrate. Wie schnell sollte ein Paket übertragen werden, wie lange dauert es tatsächlich? so kann das Protokoll vor einem Paketverlust die SWG verkleinern, bevor ein Paketverlust auftritt.

Während der Initialisierung speichern alle Knoten ihre Kantenkosten zu ihren Nachbarn und wählen dabei immer den kürzesten Weg. Während der Initialisierung umfassen die gespeicherten Kantenkosten nur die direkt an den Knoten liegenden Kanten. Danach wird die Liste aktualisiert, Indem die Knoten allen direkten Nachbarn ihre eigene Kostentabelle übertragen. So erhält Knoten D Informationen dazu, wie hoch die Kosten von D über C, zu allen mit C verbundenen Kanten zu den verbundenen Knoten ist. Sollte eine neue Strecke, oder eine alte, aber kostengünstigere Strecke berechnet werden, wird diese in den Listen überschrieben. Sind alle Pfade zu einem Knoten gefunden und berechnet worden, werden die Kantenkosten grün markiert und somit als günstigster Weg festgelegt. Die Aktualisierung wird so oft wiederholt, bis sich keine Werte mehr ändern.
